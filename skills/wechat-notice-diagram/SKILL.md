# 通知流程图子 Skill

把已经核对过的通知事实转成“单屏优先”的 Mermaid 流程图，并保留一份适合手机阅读的省流图。它只负责表达事实，不负责猜测、合并事项或发送消息。

## 输入契约

调用前必须已有结构化事实：对象、事项、材料、步骤、截止时间、提交方式、班级统一收交标记、来源和待确认项。缺失字段在内部记录为未知，对外图不显示“未说明”“未提供”等占位字段，不用常识补齐。一个事项独立处理，按可读性决定图数；交错事项先拆开。

用户提供的原文中只要有原通知 HTTP(S) 链接，必须先实际打开并读取链接正文，以及影响办理步骤的链接内附件或图片文字，再与用户原文核对。由 `wechat-notice` 主 Skill 调用时，检查输入是否包含主 Skill 实际读取的链接地址、相关正文内容、来源位置和读取状态；缺少这些材料就先读取链接，不能仅凭网址、标题、卡片、搜索摘要或转述制图。独立调用本 Skill 时自行读取。链接无法读取时说明原因并请求可访问的原文材料，不把未核对图稿作为正式结果；没有链接时按已提供事实制图并注明无链接可核对。

独立调用时检索网页中与当前事项有关的附件或必要图片，下载到用户指定的本地目录；未指定时使用 `~/Downloads/WeChatNotice/<事项标题>/`。安全处理文件名，同名文件分别编号；核实文件存在、非空且可读取后，提取制图所需事实。由主 Skill 调用时复用主 Skill 已下载并核实的附件，不重复下载。对话中列出所需附件的来源网址和本地绝对路径；下载失败标明原因，不把网页卡片当作文件。

制图前使用同一事项的合并事实：链接、用户原文和相关附件中的增量信息合并，相同或近似的事实去重，较具体且不冲突的值保留具体信息。明确更正替换旧值；无法判定的冲突列为待确认，不在图中任选或拼接。由主 Skill 调用时核对其合并结果和各字段来源；独立调用时自行完成合并，不只取其中一份材料。

生成前后做逐字段核对：对象、事项、每项材料、每个步骤、实际截止、提交方式和每个分支的已知值都必须出现在图或配套省流文字中；原文只写“班级”就不能扩写成“全体同学”，已给出的日期或提交方式不能省略。只能使用输入事实或明确的参数计算结果。

## 先理解语义，再制图

语义规则唯一来源是 lite 的 [共同语义理解规则](../wechat-notice-lite/references/semantic-understanding.md)，必须读取并遵循；diagram 不另维护一套不同的理解规则。

由主入口调用时，接收它在 lite 信息搜索与来源核对之后形成的共同语义结果，包括目的、对象、参与性质、行动条件、事实来源、步骤依赖/并行/选择关系、日期约束、完成条件与待确认项。直接复用这份结果选择布局、安排节点和箭头，不重复完整语义理解，不重搜已取得资料，不自行推翻或改写共同结果。缺少共同结果或发现资料缺口时返回主入口的共同阶段补齐，再更新受影响的图文。

独立调用 diagram 时，先读取与核对来源材料，再执行同一份共同语义规则，然后布局出图。主入口模式按“共同语义结果 → 布局 → 出图 → 对照共同结果复核”执行；独立模式在这之前自行完成资料与共同语义阶段。先后依赖串行，独立动作与材料并行，互斥选择分支；语义优先于节点数量、单屏目标和模板。省流图也保持相同对象、参与性质、行动条件和动作关系。

默认保留已核对原文中的适用时间，不重新计算提前日期。原文明示班级截止时直接使用；主 Skill 给出的提前建议未获用户确认时只在通知包末尾对话中提醒，不进入图片。班级统一收交的默认建议是把上级截止日算第 1 天、往前数到第 3 天（截止日期减 2 个自然日）的北京时间 12:00；主 Skill 必须算出具体年月日，在通知包末尾代码块之外加粗给用户看，用户确认后才更新图稿。`show_original_deadline` 只控制已有另一已确认班级截止时是否额外展示上级日期，不隐藏唯一适用时间。所有时刻转成北京时间，使用 24 小时制 HH:MM，跨日同步转换日期；仅日期不补时刻，时区有歧义先确认。

## 图形规则

- 默认一页总览只表达来源已有的通知事实和语义关系；独立信息并列，依赖步骤串行，选择事项分支。图内不得加入通知制作人的审核、转发、渲染或提醒审批流程；只使用原文明确的办理完成条件，无完成条件时不补造终点。
- 总览只保留关键关系。是否合并节点由语义决定，不按步骤数量硬合并；合并不能抹掉先后依赖、不同对象或行动条件。独立材料可共用一个清单节点。
- 完成语义理解后，若步骤、材料、分支较多或文字过长影响单屏可读性，可按总览、办理细节、判断分支拆图。数量仅用于判断容量，不决定关系；确有先后依赖的步骤串行，独立动作和材料并列。
- 每张图控制在手机/单屏可读范围；备用渲染以不超过约 1600×1100 像素为目标。仍放不下时继续按步骤或判断点拆分，不缩小文字硬塞。
- 章节顺序通过必要的主题标题和对话中的图序表达；“承接上一图”“见后图”“详见前图”等跨图衔接语默认只放在配套对话文字中，不写进图片标题、副标题、节点或页脚。每项材料、每个步骤和每个分支必须在某张图或配套省流文字中出现，不能因拆图而省略事实。
- 未确认的收交建议、日期计算解释不进入图；个人事项不添加“不提前”等制作说明。
- 图示、正文、省流版和提醒使用同一已核对或用户已确认的适用时间，未确认建议不改变它；原件不改。
- 补充、更正或条件选择用明确分支；不确定关联用“待确认”，不要仅因消息相邻合并。
- Mermaid 标签转义引号、方括号、花括号和换行；长材料放配套对话文字或办理细节图，避免总览过密。
- 图内文案净化：默认只保留通知事实、办理步骤、必要的主题标题和影响行动的事实待确认提示。先理解内容的语义与用途，删除不影响读者行动的解释性话语、无关套话和重复文案；不能把当次对话的修改方式写成长期规则，也不能为精简而删掉必要事实。制作过程、编排导读、核对解释和渲染说明放在配套对话或审核记录中；不得自动加入“承接上一图”“图中保留原句”“为方便阅读”“本图展示”“Mermaid 源码同时保留”等解释性文字。事实缺口可简写为“站位待补充”等，不把处理过程写进图。用户明确要求某句说明时才加入。生成前检查全部可见文案，渲染后再检查实际图片的标题、节点、副标题、页脚及备用渲染器自动附加文字；发现冗余说明时同步删除源码和渲染中的文字，并收紧其占用的留白。
- 链接显示规则：URL 只能完整显示（包括协议、域名和完整路径）或完全不显示；不得截断域名、缩写路径或使用“网址”占位。若完整 URL 会挤压步骤布局，把它移到办理细节图或配套对话文字，而不是显示半截链接。
- 多步骤事项布局：当通知包含多个连续操作步骤时，各端口或分支必须保留独立的串行步骤，不得把整条路径压缩成一个“电脑端/移动端”节点。可按审查需要使用三种布局：纵向步骤卡（手机优先）、双泳道时间线（端口对照）或选择分支流程（先选端口再串行）；先依据语义选择合适布局，确有取舍时才提供候选，不按固定规则制造多份重复图。
- 折返路线校验：跨行连线必须从当前步骤指向下一序号；出图后沿每条箭头逐一核对 `1→2→3→…`，同时检查卡片数字和阅读方向一致。不能让连接线跳过步骤或指向已完成的步骤。

## 模板选择

模板不是唯一解。用户可以在请求中手动指定 `template`；未指定时，根据事项复杂度选择，并在存在明显取舍时提供可审查的候选稿。

- `comprehensive_overview`：综合信息总览。模仿“通知标题/来源 → 日期或关键事实卡片 → 办理入口 → 分支步骤 → 完成结果 → 必要提醒”的一张图，适合用户要求“把所有信息总结在一张图里”或制作通知海报。它可以汇总全篇信息，但每个端口的操作步骤仍必须独立串行，不能把完整路径塞进一个节点；分支只在共同结果处汇合。
- `overview`：一页总览。只放对象、事项、截止、提交出口，细节移到后续图。
- `vertical_steps`：纵向步骤卡。电脑端、移动端或其他分支各自向下串行，优先保证手机可读。
- `swimlanes`：双泳道时间线。不同端口或角色并排推进，适合逐步对照。
- `decision_flow`：选择分支流程。先展示“选择办理端/条件”，再进入各自的串行步骤。
- `mobile_summary`：省流图。只保留入口、核心步骤和共同结果，不重复来源、口号或装饰性元信息。

`comprehensive_overview` 按已理解的事实关系组织，不提供带制作流程的固定骨架。仅在原文确有电脑端、移动端时设置相应选择分支；不能从模板补造端口或完成条件。

手动指定示例：`template=comprehensive_overview`、`template=vertical_steps` 或 `template=swimlanes`。如果一张综合总览会导致文字过小或步骤无法逐项阅读，保留综合总览作为索引图，并追加办理细节图，不得为了塞进一张图而截断事实。

## 视觉样式

视觉样式与布局模板独立选择。默认 `style=paper`（暖纸质）；用户明确指定 `style=sage` 时使用鼠尾草绿。不再把清透蓝、墨紫对比作为常规候选；除非用户另行要求，不必每次生成多种颜色让用户重选。

- `paper`：暖白纸底（约 `#FAF7F0`）、深灰文字、陶土色重点（约 `#AA6249`），低噪声细边框。用重点色标记步骤编号、连线或最关键动作，不给每个事实配一种颜色。
- `sage`：偏暖浅纸底（约 `#F5F5EC`）、深绿文字、鼠尾草绿重点（约 `#3F735A`），柔和浅绿日期/提示卡。保持文字与底色的清晰对比，不能为了柔和而把字变淡。
- 两种样式都应优先突出办理要求、关键日期和连续步骤；保持卡片层级、箭头方向、字号与留白一致。若在手机单屏内放不下，先精简重复信息或调整排布，不以缩小文字、截断 URL 或牺牲步骤顺序换取美观。

## 布局选择与拆图

先依据语义判断串行、并行和条件分支，再按手机可读性拆图。短事项可以一页事实总览，长事项按办理细节或判断主题拆分；章节数和节点数不是事实关系依据。每张图只表达通知事实，不加入“用户审核后转发”“核对后办理”“承接上一图”等制作流程或导读节点。图序与跨图关系写在配套对话里；原文确有核验步骤时保留具体核验动作，不与制作人的审核混淆。没有截止、材料或渠道的事项直接省略对应卡片，必要缺口在对话审核说明中列出。

辅助生成器只能渲染语义核对后的结构化关系：`steps` 内确有依赖时使用 `steps_relation=sequential`，独立动作使用 `steps_relation=parallel`；复杂端口和混合依赖直接编写相应 Mermaid，不把不同端口塞进一条步骤链。生成器不是语义理解的替代品。

## 输出

在对话中同时展示 Mermaid 源码、按章节的渲染图片和省流图片；图片直接内嵌，不只给路径或下载链接。渲染所需的首张技术文件可使用 `flowchart.mmd/png`，后续章节使用 `flowchart-02-*.mmd/png`，但文件只是处理产物，不能代替对话输出。内容较多时按事项、章节分段继续在对话中展示。Mermaid CLI 不可用时在对话中展示源码和本地备用渲染，并在审核说明中标记。图片要核对中文字体、文字截断、日期、手机可读性、单屏高度和原截止时间开关。

## 审核边界

图、文案、原件清单和提醒绑定同一通知版本。用户修改事实、日期、附件、目标群或图稿后，旧批准失效；未审核前不得调用微信发送能力。
